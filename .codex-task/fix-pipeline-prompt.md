### Finding #8 [P1] backend/app/pipeline/stages/proposition_stage.py:77 — LLM-assist response parsing in EarlyPropositionStage is never exercised with actual LLM output
Why: `_assist()` is the only code path that turns untrusted LLM JSON into `Proposition` objects: it validates bounds (`0 <= start < end <= len(text)`), builds `ActorRef`/`AdjudicatorRef`, and swallows `KeyError`/`TypeError`/`ValueError` per item. The only test that reaches this method, test_proposition_stage.py:125 (`test_llm_assist_is_routed_through_proposition_task`), uses `FakeLLM()` with its default `response = {"propositions": []}` -- the for-loop body at proposition_stage.py:77-97 (bounds check, role/validator_mode extraction, Proposition construction, and the except clause) never runs. Malformed LLM output (out-of-range spans, missing required keys, an invalid disposition/proposition_type value) is exactly the failure mode this parsing exists to guard against, and it is completely unverified -- a regression here (e.g. the bounds check silently inverted, or a KeyError not actually caught) would only surface against a live LLM in production, not in CI.
Suggested fix: Add test cases that pass FakeLLM(response={"propositions": [...]}) with (a) a well-formed item to confirm a Proposition is built and merged with the lexicon candidates, (b) an out-of-bounds start/end pair to confirm it is silently skipped, and (c) a malformed item (missing proposition_type) to confirm the except (KeyError, TypeError, ValueError) branch drops it without raising. Also add a case where self.llm.structured raises, to confirm the outer try/except at proposition_stage.py:34-37 still returns the lexicon-only candidates.

### Finding #11 [P1] backend/tests/test_proposition_byte_neutral.py:137 — Byte-neutral proof never runs the parallel pipeline it claims to protect
Why: The whole point of this characterization test is to prove that, with propositions off (the shipped default), production output is unchanged. But it builds `PipelineOrchestrator(store, stages=stages)` with an explicit `stages=` list, which routes through `_run_flat` (orchestrator.py:381-383, 621) -- a minimal legacy sequential loop the test constructs itself as `[IngestionStage(), NormalizationStage(), EarlyPropositionStage(llm=None)]`. The actual production entrypoint (`app/api/routes/enrich.py:106`, `PipelineOrchestrator(_job_store, llm=fallback_llm, task_llms=task_llms)`, no `stages=`) instead goes through `_run_parallel` and `build_pipeline_config`, which is exactly where this diff wires the new stage into the system: `config.early_proposition = EarlyPropositionStage(...)` (orchestrator.py:156) and the new `run_early_proposition` coroutine added into `asyncio.gather(...)` (orchestrator.py:503-535). A bug introduced specifically in that gather wiring -- an exception in a sibling coroutine changing behavior, an ordering effect, a stage being wired even when the flag is off -- would not be caught by this test despite its name and stated purpose, because the test never touches `_run_parallel` or `build_pipeline_config` at all. This is the classic 'mirror test misses the machine' shape: the test proves a synthetic two-stage pipeline is stable, not that the real one is.
Suggested fix: Add a companion assertion (or a second parametrized capture) in test_proposition_byte_neutral.py that builds the orchestrator the same way production does -- `PipelineOrchestrator(store, llm=None, task_llms=TaskLLMs())` with no `stages=` kwarg -- so `_run_parallel`/`build_pipeline_config` actually executes with `proposition_extraction_enabled` at its default (False), and compare its output (or at least the propositions field and export/SSE emissions) against the same fixtures. If a full parallel-path byte-for-byte fixture is too heavy, at minimum assert `job.result.propositions == []` after a `_run_parallel` run with the flag off, so the gather wiring itself is exercised by this suite.

### Finding #14 [P2] backend/app/pipeline/orchestrator.py:535 — Proposition citation edges race early-individual stage (parallel gather)
Why: In the production parallel orchestrator, run_early_individual and run_early_proposition run concurrently under asyncio.gather. EarlyIndividualStage.execute awaits run_in_executor twice (citation_extractor.py:204,209) before assigning job.result.individuals (individual_stage.py:118), so when the proposition coroutine's synchronous extract() runs it almost always reads the still-empty individuals list — PropositionExtractor._build iterates job.result.individuals to attach CitationEdge records. Result: pipeline-produced proposition candidates have empty/nondeterministic citation_edges, while the sequential build_stages path (synthetic runner) and GoldStore's baseline path (which re-runs the extractor on the completed job) produce edges. The lexicon-only baseline comparison the intent calls for will spuriously diff against pre-selected candidates on citation_edges alone, corrupting the instrument-validity comparison.
Suggested fix: Enforce the ordering the extractor assumes: in the parallel phase, run early_proposition after early_individual inside one chained coroutine (async def run_individual_then_proposition: await run_early_individual(j); await run_early_proposition(j)) and gather that instead of the two separately — matching build_stages' sequential order. Alternative: move citation-edge derivation out of the early extractor into a post-parallel enrichment step.
