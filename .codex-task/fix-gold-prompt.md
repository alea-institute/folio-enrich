### Finding #2 [P1] backend/app/services/gold/store.py:185 — Gold export discard strips demo jobs' cleanup protection (shared PROTECTED_JOB_IDS)
Why: GoldStore._save() writes into the same process-wide `PROTECTED_JOB_IDS` set that demo_seed.py uses to keep the 22 pre-baked exemplar demo jobs from ever being deleted by retention cleanup. demo_seed.py only ever adds to that set (`PROTECTED_JOB_IDS.add(str(job.id))`), but GoldStore._save() both adds and *discards* from it based on whether a gold annotation session has been exported (`PROTECTED_JOB_IDS.discard(session.job_id)` once `session.exported_at` is set). Nothing stops an annotator from opening the Propositions tab on a loaded demo job (`currentJobId` is the demo's job id whenever a demo is hydrated and `status === 'completed'`) and running a full annotate-and-export cycle against it. The moment that gold session exports, the demo job's id is discarded from `PROTECTED_JOB_IDS` — permanently, until the process restarts — even though demo_seed.py never re-adds it outside of startup. If the server has been up long enough that the job's `updated_at` (refreshed only at startup) falls outside `job_retention_days`, the next `cleanup_expired()` pass can delete that demo job, because it is no longer in `PROTECTED_JOB_IDS` and, since the session was exported, it is also absent from job_store.py's new `unexported_job_ids` scan (job_store.py:130-141, which explicitly excludes exported sessions). Two unrelated features (`demo_seed.py`'s one-way protection registry and `GoldStore`'s per-session export gate) are sharing one mutable global set with conflicting write semantics, and the second feature can silently undo the first's protection guarantee.
Suggested fix: Stop mutating the shared `PROTECTED_JOB_IDS` set from GoldStore._save() (drop both the `.add()` and `.discard()` calls at store.py:182-185). job_store.py's `cleanup_expired()` already independently and correctly derives gold-session job protection every run by scanning `gold_sessions/*.json` for sessions missing `exported_at` (job_store.py:130-141's new `unexported_job_ids` set) — that scan is sufficient on its own and doesn't have this cross-feature side effect. If in-memory bookkeeping is still wanted for gold sessions specifically, give it its own dedicated set/module instead of reusing demo_seed.py's append-only `PROTECTED_JOB_IDS`.
Evidence: [
"backend/app/services/gold/store.py:180-186 -- async def _save(self, session): ... if session.exported_at is None: PROTECTED_JOB_IDS.add(session.job_id) else: PROTECTED_JOB_IDS.discard(session.job_id)",
"backend/app/services/demo_seed.py:58-61 -- job = Job.model_validate(job_dict); job.updated_at = now  # keep fresh so cleanup never targets it; await store.save(job); PROTECTED_JOB_IDS.add(str(job.id))  -- demo_seed only ever adds, never discards, for the same shared set",

### Finding #3 [P1] backend/app/services/gold/store.py:279 — GoldStore session mutations race — no lock guards read-modify-write
Why: An annotator can silently lose an accept/edit/discard decision when two actions on the same annotation session land close together — e.g. clicking Accept on one candidate card and then Discard on another before the first request finishes, or the 'a'/'d' keyboard shortcuts fired in quick succession (frontend/index.html's savePropositionOutcome does not disable buttons or serialize requests while a PATCH is in flight). Every mutating GoldStore method (record_candidate_outcome, add_hand_added, add_learning, set_blind_segment, reveal_blind_segment, record_coverage_pass, export) reads the whole session file, mutates an in-memory copy, and writes the whole file back with no lock, version check, or CAS. If request B's `_load` (store.py:279) runs before request A's `update`/`_save` (store.py:266-268, 178-185) completes, B's later write is based on the pre-A snapshot and clobbers A's change on disk — A's outcome silently reverts to its prior state with no error surfaced to either request. This is exactly the concurrent-PATCH race the annotation UI's per-action autosave pattern is prone to, and it corrupts the gold dataset this whole phase exists to produce.
Suggested fix: Add a per-session asyncio.Lock in GoldStore.__init__ (e.g. self._locks: dict[str, asyncio.Lock] = defaultdict(asyncio.Lock)) and wrap the load→mutate→save critical section of every mutating method (record_candidate_outcome, add_hand_added, add_learning, set_blind_segment, reveal_blind_segment, record_coverage_pass, export) in `async with self._locks[session_id]:`. This is sufficient because the backend runs as a single-worker asyncio process (uvicorn --host ... --port 8731, no --workers), so an in-process lock serializes all writers to a given session without needing cross-process file locking.
Evidence: [
"backend/app/services/gold/store.py:279 -- session = await self._load(session_id)",
"backend/app/services/gold/store.py:296-299 -- candidate.proposition = current; candidate.outcome = outcome; candidate.explicit_unresolved = explicit_unresolved; await self.update(session)",
"backend/app/services/gold/store.py:178-185 -- async def _save(self, session): ...; _atomic_write(self._path(session.session_id), session.model_dump_json(indent=2)) -- writes the entire session snapshot with no version/lock check"
]

### Finding #7 [P1] backend/app/api/routes/gold.py:147 — Unauthenticated /gold endpoints allow server-side file writes on public deploy
Why: On the public demo (enrich.openlegalstandard.org) any anonymous visitor can submit an enrichment to obtain a job_id, POST /gold/sessions, then POST /gold/sessions/{id}/export. Export writes attacker-controlled JSONL/brat files plus overwrites manifest.json and README.md under the server repo tree (export_dir resolves to <repo>/backend/eval/gold/propositions), with no authentication on any /gold route. This is an unauthenticated write-to-filesystem primitive: repeated exports with distinct slugs pollute and grow the server filesystem (disk-exhaustion DoS) and can clobber the shared manifest. Separately, every unexported session adds session.job_id to the in-memory PROTECTED_JOB_IDS set (store.py:183), so anonymous sessions permanently exempt jobs from retention cleanup — an unbounded-growth / retention-bypass vector. The project already gates its other mutating routes with Depends(require_admin) (folio_update.py:52), which no-ops locally but enforces X-Admin-Token when settings.admin_token is set for public deploys; the /gold write/mutate routes should carry the same guard. Filenames are slug-sanitized (_safe_slug strips path separators), so this is not path traversal, but the unauthenticated write and global-state mutation remain.
Suggested fix: Add dependencies=[Depends(require_admin)] to the state-mutating/file-writing /gold routes (at minimum export, create_session, and the blind-segment/coverage/learning POST/PATCH routes), matching folio_update.py. This leaves local/trusted deploys unauthenticated (admin_token empty) while requiring X-Admin-Token on the public site.

### Finding #16 [P3] backend/app/services/gold/store.py:290 — edit_kind misclassifies UI boundary edits as 'both'
Why: record_candidate_outcome computes the field-edit half of edit_kind by diffing model dumps that exclude only start_char/end_char — but not the derived 'text' field. The frontend always recomputes text from the span (index.html:12034 text: fullText.slice(start, end)), so any boundary adjustment made through the UI also changes text, making the field comparison True and classifying a pure boundary edit as 'both'. The edit-kind provenance metric in the gold records (the audit trail the intent asks for) is therefore systematically skewed: 'boundary' will essentially never appear for UI edits. The existing test only passes because it constructs a boundary edit whose text happens to stay identical.
Suggested fix: Exclude the span-derived field from the comparison: current_fields = current.model_dump(exclude={"start_char", "end_char", "text"}) (and the same for original_fields), so 'field' means a genuine label/role/disposition change. Assumption: text is always derivable from the span; if free-text overrides are ever allowed, compare text against fullText[start:end] instead.
Evidence: [
