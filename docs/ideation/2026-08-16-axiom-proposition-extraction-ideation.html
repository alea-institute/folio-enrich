Grounding Context

Codebase context. folio-enrich runs a 16-stage pipeline (parallel extraction ∥ post-parallel grounding); triples are the only extraction type with no LLM task and no normalization layer — predicates like respond On and subjects like I. BACKGROUND ship raw. folio-insights is production (14K LOC, 691 tests, Railway) and imports folio-enrich through a fragile sys.path bridge that has silently broken at least twice; folio-resolve==0.4.0 already replaced one bridge seam with a pinned library. folio-insights' v1.0 UAT documented ~90% hallucinated FOLIO IRIs until deterministic folio-resolve grounding was merged — in-house proof of the uploaded spec's "grounding as filter, not union" thesis. Two schema gaps are documented in insights' own sources: no field captures who asserts a proposition, and extracted citations don't bind to the propositions they support. In enrich, every concept that fails FOLIO resolution is silently dropped (resolution_stage.py:282, no else-branch).

External context. SPIRES/OntoGPT validates extract-then-ground (biomedical only; ~41 F1 on relations); LangChain's strict_mode ships schema filtering at the extraction layer; the ECHR argument-mining corpora (Habernal, 15k+ spans, 80% IAA) are the closest prior art for the proposition taxonomy; LLMs4OL 2025 finds LLMs need human-in-the-loop for ontology additions. Market scan: legal knowledge graphs are table-stakes (NetDocuments, Noxtua, LegalOn), but nobody unifies span-level annotation with axiom extraction in one pipeline.

User-supplied spec. The uploaded three-stage build spec (LLMGraphTransformer → dedupe/normalize → SPIRES-as-gatekeeper, with doc-type-aware chunking, Jena/Fuseki storage, and per-stage model/caching economics) was treated as leverageable input, not constraint.

1. The Proposition System

Merged 1–6system-wide · all five axesConfidence 85%Complexity High (staged)
Unifying principle
Everything in the system is a proposition with an asserter and a validator — including the system's own outputs. A party asserts; a court validates (accepted / rejected / revised / unresolved). The pipeline asserts an extraction; the grounding filter validates it. A reviewer asserts approval; the signed action validates a proposition into axiom status. The system asserts a candidate FOLIO addition; FOLIO governance validates it into the ontology. One relation, applied recursively — this is what makes six ideas one system.
The two-exit gate
The keystone mechanism: the grounding gate has two outputs, and nothing is discarded. Candidates that pass become grounded propositions (and may be promoted to axioms through the validation lifecycle). Candidates that fail become structured near-miss records (and may be promoted into FOLIO as proposal packets). Precision filtering and ontology enrichment are the same gate, viewed from its two exits.

The repo-boundary rule that routes every component: does it need more than one document? No → folio-enrich. Yes → folio-insights. Is it vocabulary or logic both need → folio-propositions. The five remaining sys.path bridge adapters (folio_service, embedding_service, normalizer, aho_corasick_matcher, citation_extractor) get extracted to the library tier on the folio-resolve precedent, with consumer contract tests running in folio-enrich's CI.

The double-entry ledger (schema spine)

Every proposition carries two mandatory sides — asserted_by and adjudicated_by, where null is a first-class state — plus a disposition enum and CiTO-style typed citation edges (supports / distinguishes / overrules / follows / cites-record-evidence). Asserters and validators are TripleLink-style edges to already-extracted Individuals. Unbalanced entries mechanically name the missed proposition types:

asserted_byadjudicated_byWhat it names
partycourtthe classic litigated proposition (accepted / rejected / revised)
partynullopen position — asserted, never ruled on (waived, moot, unreached)
both partiesnull / pro-formastipulation — settled bilaterally (sometimes court-approved)
court (assumed)court (declined)arguendo — assumed without deciding
nullcourtjudicial notice — validated with no party assertion

Axiom is not a sibling type: it is the status a proposition earns through validation events (folio-insights' promote / demote / supersede SignedActions already implement the lifecycle). SVO triples are contained fragments. Shapes are parameterized per Ontology aggregate — litigation shape for FOLIO, disputatio shape for the Catholic Canon ontology already live in production.

The library is carved out of insights, not built beside it

folio-propositions and folio-insights are not rivals — one is a vocabulary, the other an application — but insights already contains a proposition vocabulary (its shard models in envelope.py / subtypes.py). Building folio-propositions as a new schema alongside it would create two competing definitions of "proposition" — the schema-level version of the sys.path bridge. So the library is the extraction of insights' vocabulary layer (plus the ledger design) into the shared tier, which insights consumes back — the folio-resolve playbook, replayed for the domain model. Alternatives weighed and rejected: making insights itself the shared dependency (drags an application's dependency weight into enrich, inverts the layering, and manufactures a circular import since insights already consumes enrich components); or no library at all (two definitions, silent drift, a mapping layer nobody owns).

The unification is real, not forced — insights' five shard types are configurations of the one Proposition model:

insights shard typeIn the ledger vocabulary
simple_assertionproposition with a plain balanced entry
hypothesisasserted_by = system (generated), adjudicated_by = null

disputed_propositiona thread of propositions linked by stance edges (utrum → objections → respondeo)

The last row is the boundary in miniature: single-document shapes belong to the library; cross-document composites belong to the app. The document/corpus rule routes the shard types themselves.

Build decisions (settled 2026-08-16)

Decision · Library timing
Models-first hybrid. folio-propositions is created in Phase A holding only the Pydantic models + interchange schema, after the gold-doc exercise validates them. Stage logic starts in folio-enrich and migrates into the library as it stabilizes. No sixth bridge adapter ever forms; no premature API freeze.
Decision · v2.0 alignment
The folio-propositions model and folio-insights' v2.0 shard-envelope redesign are one work item. Insights' v2.0 PRD (review 2026-08-23) defines typed shards with 15-field provenance envelopes — that is proposition-vocabulary work. The ledger schema, typed citation edges, and axiom-as-status go into that review as the proposed v2.0 schema, authored in the library; insights v2.0 consumes it. The review date (targeted 2026-08-23) is a soft target — the schema ships to review when it has survived annotation, not on a calendar gate.
Decision · Sequencing & annotation process
Parallel tracks with an LLM-assisted annotation tool. An LLM-backed tool pre-selects candidate proposition spans and applies rudimentary classifiers from the working taxonomy; the annotator (Damien) edits or deletes pre-selected spans, adds his own, and can augment the taxonomy with new proposition types as he goes. Gold opinions span court levels — district, appellate, supreme; state and federal — so the taxonomy is falsified against genre diversity, not one document's habits. Agile: the MVP skeleton (stage scaffolding, tab plumbing, review controls) is built in parallel, since the annotation tool's pre-select + edit/add surface is the same component as the Propositions tab's review controls — the tracks converge on shared code, and every gold annotation doubles as labeled eval/training data.

Rationale
Answers the original question — "is folio-insights just a feature of folio-enrich?" — with something better than merge or status quo: one product family, three declared layers, routed by the document/corpus rule. Nearly every mechanism reuses shipped, tested code (the resolver, the linker, BranchJudge, the review UI, the signing envelope); the genuinely new build is the schema, the reporting-verb lexicon, the near-miss store, and the wiring. Strategically it makes the ecosystem FOLIO's upstream intake — a position no competitor in the market scan occupies.
Downsides
It is a program, not a feature — five phases, two repos, one new library, and FOLIO governance buy-in for the flywheel's final leg. Cross-job storage for near-miss records is new infrastructure (enrich is per-job filesystem today). Threshold calibration (novelty, confidence bands) needs the gold set first. Attestations are single-signer until insights' deferred N-of-M multi-sig lands. Discipline risks: the ledger invariant degenerates if null-typing is sloppy, and the library boundary only pays rent if the contract tests actually gate CI.
